# Панель врачей Медси Бота

## Timeweb

- `DOCTORS_ENABLED=1` включает `/doctors`. Удаление флага отключает страницу, API и фоновую синхронизацию. Записи в PostgreSQL сохраняются.
- Вход по умолчанию использует `NEXT_TUTOR_LOGIN` и `NEXT_TUTOR_PASSWORD`. Для смены учётных данных врачей задайте одновременно `DOCTORS_LOGIN` и `DOCTORS_PASSWORD`. Врачебная сессия использует собственную cookie.
- `DOCTORS_EXCLUDED_PHONES` принимает список тестовых телефонов через запятую. Этот фильтр применяется при чтении телефонной книги бота.
- `DOCTORS_GREENWOOD_SHEET_ID` включает чтение реестра «Стационар Гринвуд». Нужен ID между `/d/` и `/edit` и доступ на чтение по ссылке. Бот делает только анонимный запрос к вкладке «5 этаж» за ФИО и датой поступления. Если подтверждён столбец выписки, задайте `DOCTORS_GREENWOOD_DISCHARGE_COLUMN` (одна буква A–Z, кроме C и G); тогда читается и эта дата как резервная после правки врача и плана. По умолчанию столбец выключен. Строки с пустой или нераспознанной датой поступления видны, но для них отключены медицинские даты, автоматическое сопоставление и редактирование до заполнения реестра. Дата из таблицы помогает различать повторные госпитализации и не отображается как клиническая дата на карточке. После успешного обновления раздел показывает только детей, которые сейчас есть в таблице. Открытый список проверяется каждые 30 секунд. При временном отказе Google панель показывает последний полученный список, если он есть в памяти процесса. Изменения при недоступном реестре отклоняются.
- Без `DOCTORS_GREENWOOD_SHEET_ID` проверять интерфейс можно со списком из PostgreSQL. Телефоны и имена родителей доступны в карточке «Телефоны». В режиме Google контакты на карточках пациентов требуют подтверждённого соответствия между строкой и профилем. В текущей вкладке общего идентификатора нет. Для ручного подтверждения оператором доступен `DOCTORS_VERIFIED_CONTACT_LINKS`: JSON-массив пар `[идентификатор строки текущего пребывания из /doctors/api/patients, идентификатор ребёнка из /doctors/api/phones]`. Оба идентификатора непрозрачны и доступны только после врачебного входа. Оператор должен отдельно подтвердить личность по надёжному источнику; совпадение имени само по себе не является подтверждением. Связи действуют только для конкретной строки и даты поступления, требуют привязанного `child_id` и совпадения имени/фамилии, не переносятся на новую госпитализацию. Дубли или невалидная конфигурация отключают все такие связи. Не публикуйте значения в Git или логах.
- `DOCTORS_DISK_ROOT` задаёт путь к папке пациентов, например `disk:/Документы/Пациенты`. `DOCTORS_DISK_TOKEN` берётся из секретов Timeweb. `DOCTORS_DISK_INTERVAL_MS` по умолчанию составляет 300000 мс.
- `DOCTORS_DISK_TEST_WRITE=1` вместе с `DOCTORS_DISK_WRITE_TEST_ROOT`, совпадающим с `DOCTORS_DISK_ROOT`, разрешают запись в явно заданную тестовую папку с копиями. Перед включением настройте закрытый S3 и срок хранения объектов с префиксом `doctor-plan-backups/`. В рабочей среде с оригиналами оставьте тестовые параметры пустыми.

## Подключение Яндекс OAuth

1. Создайте OAuth-приложение в [Яндекс OAuth](https://oauth.yandex.ru/). Выберите право чтения Яндекс.Диска (`cloud_api:disk.read`). Для отдельной учётной записи с тестовыми копиями и проверкой записи добавьте право `cloud_api:disk.write`.
2. Авторизуйтесь как владелец нужных папок, пройдите согласование и получите токен через [официальный OAuth-процесс](https://yandex.com/dev/disk/rest/).
3. Запишите токен в переменную `DOCTORS_DISK_TOKEN` в настройках приложения Timeweb. Укажите путь, заданный в `DOCTORS_DISK_ROOT`. Пароль от Яндекс-аккаунта для бота не требуется.

## Изменение выписки

Правка врача сначала фиксируется в PostgreSQL. Синхронизатор проверяет принадлежность документов, выбирает планы текущего пребывания, проверяет даты во всех файлах и сохраняет копии перед загрузкой. После каждой загрузки скачивает файл и сверяет хеш. Если процесс прерывается после загрузки части файлов, повторная проверка пропускает планы с уже установленной датой. В интерфейсе отображается одна дата. До синхронизации приоритет у сохранённой правки врача. Без ожидающей правки используется итоговый план текущей госпитализации, затем самый свежий доступный план. При равной свежести сравнивается дата в названии файла, затем выбирается более поздняя дата выписки. При записи правка врача применяется ко всем проверенным планам текущего пребывания с сохранением резервных копий. Неоднозначность принадлежности документа или несовпадение версии при загрузке блокируют запись или откладывают её до повторной проверки. Независимая правка даты (отличная от исходной и желаемой) блокирует всю операцию до записи любых очередных файлов. Конфликт не повторяется автоматически; после проверки документа врач должен явно подтвердить выбранную дату и заново сохранить её относительно свежего снимка. Для реестра дата начала в плане должна совпасть с датой поступления в строке: пересечение диапазонов недостаточно, поскольку оно может принадлежать старому пребыванию. Если даты расходятся, оператор должен сверить источники; без даты пребывания запись в Excel отключена. Ошибка одной папки не останавливает обработку остальных пациентов. Перед записью повторно проверяется актуальный состав реестра. Новый план без ранее известной версии допускает запись только при пустой выписке либо уже совпадающей дате.

Яндекс.Диск не предоставляет проверенную атомарную операцию сравнения версии при перезаписи через ссылку загрузки. Между заключительной проверкой и загрузкой остаётся окно для внешней правки. Запись с текущими настройками предназначена для тестовой папки.

## Проверка

`npm run verify` и `npm run verify:postgres-next` проверяют приложение. Для дополнительной проверки очереди на локальном чистом PostgreSQL передайте его порт в `MEDSI_DOCTORS_TEST_PG_PORT` и запустите `node --test services/postgres-next/app-test/doctors-panel.test.mjs`. Тест пользуется синтетическими документами и имитирует Яндекс.Диск и S3. CI отдельно запускает этот тест на одноразовой базе PostgreSQL 18, чтобы интеграционный сценарий не был пропущен.

## Порядок безопасного выпуска

1. Проверить обе команды CI на актуальном HEAD и отдельно выполнить PostgreSQL-тест с `MEDSI_DOCTORS_TEST_PG_PORT` на чистой локальной БД. Проверить сохранность нецелевых частей двух обезличенных XLSX.
2. В отдельном стенде настроить `DOCTORS_ENABLED=1`, исключения телефонов и при необходимости реестр. Не использовать production-секреты и медицинские данные в CI. Проверить список и роли.
3. С согласия оператора использовать отдельную учётную запись Диска и папку синтетических копий; настроить read/write-токен, `DOCTORS_DISK_ROOT`, совпадающий `DOCTORS_DISK_WRITE_TEST_ROOT`, закрытый S3 и `DOCTORS_DISK_TEST_WRITE=1`. Проверить несколько планов, резервные копии, повтор после частичного сбоя и остановку на конфликте.
4. После отдельного согласования включить чтение рабочей папки с read-only токеном и отключёнными тестовыми флагами. Проверить актуальность и однозначность соответствий, не редактируя оригиналы. Ссылка Google с доступом всем обладателям ссылки требует согласования ответственного за конфиденциальность; не размещать её в Git.
5. Запись в оригиналы не поддерживается как отдельный production-режим в текущем коде. Не обходить тестовый ограничитель установкой рабочего пути в тестовую переменную. Для выпуска записи требуется отдельное решение по конкурентному редактированию (API не гарантирует атомарность), подтверждение организации, проверенный rollback и явный production-механизм.
6. После согласования релиза проверить smoke/cutover safety, включить согласованные флаги и контролировать обезличенные ошибки. Для отключения убрать `DOCTORS_ENABLED`; существующие панели и сохранённые данные остаются. Не менять DNS, production DB/S3 или секреты без разрешения.
