- Существующий Timeweb App Platform и тот же HTTPS-домен для сайта, Node.js API, отчётов, чатов, авторизации, уведомлений и периодических задач.
- Управляемая PostgreSQL 18 (одна БД, стартовый 1 vCPU / 1 ГБ RAM) для всех структурированных данных.
- Существующий приватный Timeweb S3 — медиа и разрешённые внешние резервные копии, **без** использования S3 для транзакционных чатов/отчётов.

## PostgreSQL-код и безопасный запуск

- `services/postgres-next/sql/001_initial.sql`: 27 таблиц и индексы, не выполняется автоматически при запуске сайта.
- `services/postgres-next/src/connection.mjs`: параметризованные SQL-запросы, преобразование PostgreSQL UPSERT, транзакции, pool, TLS с проверкой CA, корректный rollback.
- `services/postgres-next/src/schema-cli.mjs`: создаёт структуру **только в пустой БД** при явном подтверждении; на каждом деплое не запускается.
- `server.js`: при `MEDSI_NEXT_STAND=1` и `MEDSI_NEXT_PG_ENABLED=1` запускает NEXT с PostgreSQL. Если эти флаги отсутствуют — остаётся старый Timeweb gateway. В текущей реализации PostgreSQL NEXT **изолирован** и не считается разрешённым production-backend.
- `.github/workflows/verify-postgres-next.yml`: Node.js 22 + временная PostgreSQL 18, регрессия NEXT и старого gateway, тесты на фиктивных данных. Если GitHub Actions красный — merge и cutover запрещены.

## Параметры подключения Timeweb

Нужны в **секретах приложения** (не в GitHub, чате, истории терминала или конфигурационном файле):

| Переменная | Назначение |
| --- | --- |
| `PGHOST` | Точный hostname PostgreSQL, выданный Timeweb (желательно DNS-имя, проверяемое сертификатом) |
| `PGPORT` | TCP-порт из панели (обычно 5432, но брать реальный) |
| `PGDATABASE` | Название созданной базы |
| `PGUSER` | Пользователь с минимальными нужными правами |
| `PGPASSWORD` | Пароль этого пользователя |
| `PG_SSL_CA_PEM` / `PG_SSL_CA_B64` | Доверенный CA сертификат сервера; TLS всегда с проверкой сертификата |
| `MIGRATION_AUDIT_HMAC_KEY` | Секретный ключ для подписи полных capture-манифестов; 32+ байта, только защищённая среда миграции |
| `MEDSI_NEXT_PG_ENABLED` | В NEXT включить PostgreSQL (`1`); **не включать в production до cutover** |
| `MEDSI_NEXT_STAND` | Только изолированный режим для подготовленного NEXT-кода (`1`) |
| `NEXT_SESSION_SECRET` | Сильный отдельный секрет сессий, не меньше 32 символов |
| `NEXT_TUTOR_LOGIN/PASSWORD/VERSION` | Согласованные параметры входа воспитателя |
| `PARENT_PASSKEY_RP_ID` / `PARENT_PASSKEY_ORIGIN` | Действующий RP ID и точный HTTPS-origin, если сохраняем passkeys |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | Прежняя пара Web Push и адрес отправителя — для сохранения подписок |
| `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Прежний приватный S3 для медиа; не создавать новый бакет |

Переменные текущего gateway при выключенном NEXT: `SESSION_SECRET`, `APP_SCRIPT_URL`, `CHAT_UPSTREAM`, `UPLOAD_UPSTREAM`, `PUSH_UPSTREAM`, `MIGRATION_SHARED_SECRET`, `REPORTS_SYNC_SECRET`; S3 использует общие `S3_BUCKET`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` и необязательные `S3_ENDPOINT`/`S3_REGION` (Timeweb defaults). Не удалять и не менять их при подготовке NEXT.

Дополнительные переменные NEXT, сверенные с кодом: `PORT` (предоставляет платформа), `MAX_UPLOAD_BYTES` (необязательный лимит), `MEDSI_NEXT_DELETION_ENABLED`, `MEDSI_NEXT_LEGACY_AUTH_ENABLED`, `NEXT_LEGACY_D1_SESSION_SECRET`, `NEXT_LEGACY_TUTOR_LOGIN`, `NEXT_LEGACY_TUTOR_PASSWORD`, `NEXT_LEGACY_TUTOR_VERSION`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Legacy-auth values применяются только после отдельной сверки сессий и подтверждения необходимости их чтения; не активировать заранее.

`PG_SCHEMA_CONFIRM`, `MEDSI_NEXT_MIGRATION_PREFLIGHT`, `MEDSI_NEXT_SEED_DEMO`, `CI`, `NODE_ENV`, `PG_TEST_INSECURE_LOCAL` — только разовые/CI-переменные; их нельзя сохранять в production-переменных. `DATABASE_URL`, `DATABASE_SSL`, `DATABASE_POOL_MAX` относятся к старому health-check-слою и не являются конфигурацией NEXT; не направлять их на купленную БД. Значения переменных в репозиторий не копировать.

### Что действительно применено

Подготовлен только код и список имён переменных. В Timeweb не сохранялись новые переменные и секреты; production-флаги `MEDSI_NEXT_STAND` и `MEDSI_NEXT_PG_ENABLED` не включались. Поскольку App Platform автоматически деплоит новые коммиты ветки `timeweb-next`, любое изменение runtime-переменных считать потенциально перезапускающим сервисом и отложить до согласованного окна.

Из-за разницы сетевых конфигураций App Platform и БД нужно проверить способ доступа: общая приватная сеть или разрешённое публичное соединение по TLS с ограничениями доступа. Публичный IPv4 не включать вслепую: проверить реальную вкладку «Сеть/Подключение» после создания.

## Что ещё не готово — обязательные блокеры для cutover

1. **Полные экспортёры и импортёры действующих данных** из Cloudflare D1/KV и Google Sheets/Apps Script: профили, госпитализации, связи родителей, сырые/распределённые отчёты, историю, состояния прочтения, настройки имён, чаты, метаданные вложений, очереди, auth/passkeys и push-подписки. В PostgreSQL NEXT уже есть отдельные безопасные модули capture для auth/passkeys/push, но остальные потоки ещё не мигрированы в PostgreSQL.
2. **Сверка источника и результата:** реестр потоков, количество записей, дубликаты, SHA/HMAC манифесты, права каждого родителя, даты госпитализаций. Заморозить старые записи на короткое согласованное окно, повторно перенести дельту, убедиться, что ничего не пропало.
3. **Полное соответствие API существующим браузерным клиентам**, включая все старые Apps Script-методы. `legacy-bridge.mjs` реализует только часть вызовов. Пока нет подтверждения E2E существующего интерфейса воспитателя, родителя, психолога и всех переходов в новую систему.
4. **Функциональный паритет:** редактирование исходного сырого отчёта и публикация новой версии, постоянная очередь повторных отправок, напоминания 3/7/21 дня, завершённое удаление профилей и медиа, push-обработка при сбоях и журнал доступа — часть пунктов в `docs/POSTGRES_FUNCTION_PARITY.md` всё ещё помечены «частично» или «нет». Для новых карточек и экрана отчётов ещё нужны live/mobile UX-проверки; отдельный неизменяемый журнал исправлений опубликованных текстов пока не реализован.
5. **Совместимость входа:** сохранить `generation_id`, passkey credential IDs/публичные ключи/счётчики, прежний RP ID и HTTPS origin, пару VAPID, действующие сессии, время создания и expiry. Проверить Face ID/Touch ID с реального телефона, а также отсутствие случайного доступа к чужим отчётам.
6. **Информационная безопасность:** одобрение организации на хранение персональных/возможных медицинских данных детей, размещение, права доступа и срок хранения, бэкапы/восстановление, аудит, выделенная учётная запись БД, TLS и закрытый сетевой доступ. Одобрение покупки PostgreSQL само по себе не подтверждает готовность обработки данных в новой инфраструктуре.

## Развёртывание без дополнительных платных ресурсов

1. Все изменения выполнять в feature-ветке и довести до зелёного CI. Сверка UI и API — только на краткоживущей PostgreSQL внутри CI с синтетическими данными.
2. Существующее приложение Медси Бот 2.0 и PostgreSQL уже подключены к приватной сети. Дополнительные платные ресурсы и публичный адрес БД не нужны.
3. После настройки защищённых переменных выполнить read-only probe по разрешённому приватному подключению без TLS и подтвердить точный состав БД. Значение 0 ГБ на дашборде не является проверкой пустоты.
4. Согласовать резервное копирование и восстановление. Схему устанавливать только после успешного probe, подтверждённой пустоты и отдельного явного разрешения; CLI проверяет отсутствие пользовательских объектов и применяет контракт 27 таблиц/5 индексов в транзакции.
5. В одобренной защищённой среде получить экспорты, сделать независимый зашифрованный бэкап, запустить идемпотентные офлайн-импортёры и сверить все подписанные HMAC-манифесты. Сейчас полных экспортёров/импортёров для D1, KV, Sheets и S3 ещё нет; до их появления gate не должен выдавать готовность.
6. Перед единственным переключением установить write-fence для старой системы; импортировать остаточную дельту; выполнить проверку полноты, прав доступа, backup/restore и основных API.
7. Утвердить единое окно переключения на приложение 2.0. До merge PR #25 проверить и исключить автоматическое обновление приложения 1.0 из `timeweb-next`; иначе merge изменит экземпляр, который нужен для отката. Порядок действий и контрольные точки приведены ниже.
8. Откат требует **плана сохранения записей, созданных после переключения**. Просто вернуть старый GitHub-коммит может потерять новые чаты и отчёты. Пока этого плана нет — не переключать живых пользователей.

## Обновление: приложение Медси Бот 2.0 подключено к приватной сети

Проверено в панели после предыдущего осмотра:

- Создано ровно одно новое приложение Timeweb App Platform «Медси Бот 2.0» (ID `282811`); тариф 1 vCPU / 1 ГБ / 15 ГБ, 510 ₽/мес при почасовом списании. Его единственная пользовательская ветка — `feature/timeweb-postgres-cutover`; production-домены не назначены. Есть только технический домен Timeweb.
- Приложение и существующая PostgreSQL 18 (ID `4228063`) теперь состоят в одной приватной сети `Daring Snipe`, адреса `192.168.0.5` и `192.168.0.4`. Дополнительные платные ресурсы не создавались.
- Пользователь разрешил соединение без TLS только к базе по RFC1918-адресу внутри приватной сети. Код принимает такой режим только при явном `PG_SSL_MODE=private_network_no_tls` и буквальном частном IPv4 адресе; остальные хосты по-прежнему требуют проверенный TLS. Это исключение применимо только к соединению внутри закрытой сети.
- Последний коммит приложения 2.0 (`96a734f`) собрался успешно и контейнер был запущен. Последняя запись о его health-check была `starting`, поэтому готовность публичного технического домена ещё не подтверждена. Параметры подключения PostgreSQL и учётные данные приложения не настроены; секреты не открывались и не менялись. Read-only probe, проверка схемы и инициализация ещё не запускались.
- GitHub workflow `Verify Medsi source` успешен на `96a734fc9ee69d2bc88a0dcc1652387016860641`; `timeweb-next` имеет отдельный HEAD `9c12b039e0c177b3207f7bce2d86e437c292b22b`.

Следующий безопасный шаг после тестирования текущего изменения — внести только защищённые переменные в приложение 2.0 и выполнить read-only probe. Установку схемы выполнять отдельно, лишь после probe, проверки пустой БД и разрешения на инициализацию. В приложение 2.0 не переносить настоящие данные до одобрения организации и реализации полного набора экспортёров/импортёров.

## Порядок переключения на приложение 2.0

1. Зафиксировать текущий деплой приложения 1.0, кандидат 2.0, привязку домена и состояние фоновых задач. Подтвердить, что GitHub и Timeweb не заменят версию 1.0 при merge. Сохранить её доступной для отката.
2. Проверить восстановление из резервной копии и выполнить полный перенос на синтетических данных. Для настоящих данных подготовить утверждённое хранилище и маршруты импорта. Проверить, что сертификат, прежний RP ID, точный HTTPS origin и пара VAPID сохранены и доступны в согласованном окне.
3. Заморозить запись во всех старых источниках, включая фоновые обработчики. Проверить запрет тестовым запросом и дождаться окончания уже запущенных операций. Зафиксировать идентификатор окна, снять дельту с момента базового переноса, применить её к 2.0 и сравнить 26 подписанных потоков для того же окна. Не открывать запись при любом расхождении.
4. Переключить основной домен на приложение 2.0 при закрытой записи. Проверить HTTPS, доступ с прежними сессиями, разделы родителя, воспитателя и психолога, а также контрольную проверку прав доступа. После принятия результата открыть запись только в 2.0. Фоновые отправки включать отдельно после проверки VAPID и тестового устройства.
5. Если проверка провалилась до открытия записи, вернуть домен на 1.0 и возобновить старые обработчики после проверки маршрутизации. Если 2.0 уже приняло запись, заморозить обе стороны, сохранить и сверить обратную дельту, включая удаления, вложения, сообщения и отчёты. Вернуть запись в 1.0 только после подтверждённого применения обратной дельты. Пока обратный перенос не отрепетирован, это блокер открытия записи в 2.0.

## Проверка интерфейса и восстановления

- На техническом домене подтверждён вход воспитателя. Разделы исходных отчётов и чатов корректно показали пустое состояние. Проверены создание и удаление одного вымышленного варианта имени. Доставка сообщений и вложений на развёрнутом приложении этим прогоном не подтверждена.
- В CI PostgreSQL 18 восстановлена из логического бэкапа. Контрольные суммы всех 25 SQL-потоков совпали. Эта репетиция не заменяет резервную копию и проверку восстановления управляемой базы Timeweb и не проверяет S3.
